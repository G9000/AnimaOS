# Complete owner-only Discord channel management

The owner selected complete channel management after the first list/create/edit implementation could not delete its test channel. Extend the native Rust connector and retain its trusted inbound receipt, single application/team owner, current-run, connector-generation and same-guild authority checks for every added operation. Approved participants, roles, display names, helpers and console messages cannot gain management authority.

Cover channel inspection, creation, modification and deletion; category placement and bulk ordering; text/announcement/voice/stage/category/forum/media settings; channel permission overwrites and permission inspection; announcement following and voice status; active/archived thread discovery, thread creation, archive/unarchive, locking, thread metadata and membership management. Thread posts may carry a bounded text starter; attachment upload remains the existing file-delivery subsystem. Guild directory channels and DMs are not mutable guild-management targets. Server role creation, member moderation, bans, server settings, invites, message moderation and Stage instance management are separate scopes.

Use separate narrowly described native tools with validated structured arguments. Reuse the existing three tools where compatible and add bounded advanced operations rather than exposing HTTP methods, URLs or arbitrary endpoints. Current guild is always selected by the host. Resolve every target, category, thread parent and announcement destination against current provider data before effects. Deletion requires the exact current channel name alongside its ID; deletion of a category does not recursively delete its children. Permission bitfields are decimal strings; permit explicit per-member or per-role overwrites without granting those users native tool authority.

Preserve bounded responses, pacing, cancellation checks, serialized mutations, durable action receipts and acknowledgement validation. Handle 204 responses explicitly. Every non-read network effect is uncertain after a transport failure or mismatched acknowledgement and must block further mutations in that run; read inspection remains available. Do not replay writes automatically. Successful deletion removes or marks stale local routing metadata, and metadata-save failure must report provider success plus local uncertainty. Keep explicit channel allowlists unchanged.

Every thread/forum starter forces `allowed_mentions: {parse: [], replied_user: false}`. Prefer single-request creation with a starter when the API supports it. If a lifecycle operation requires separate writes, preserve the created thread receipt and report partial success when a later write fails; never replay creation. Test user/role/everyone mention text and partial-failure handling.

Discord may require Manage Channels, Manage Threads or Manage Roles and guild features for particular operations. Add tool support and truthful error messages; do not grant live bot permissions, restart the stopped server or restructure live Discord during this implementation. Publish the verified extension using the owner's existing commit-and-push instruction. Verify denied-account, spoofing, console, stale capability, cross-guild/thread/category, invalid payload, uncertain effects, empty acknowledgement and metadata regressions, then run the repository Rust suites and lint.

The legacy current-thread rename tool also requires the verified owner capability and uses the same mutation fence; participant thread reading/file delivery remain separate conversation capabilities. Persist manual thread-name intent before the network effect so an automatic title cannot overwrite a manual or uncertain rename. Future user-reviewed bot invites request the additional documented channel-management permissions, including Manage Webhooks and Set Voice Channel Status, while excluding Administrator; existing roles remain unchanged.
