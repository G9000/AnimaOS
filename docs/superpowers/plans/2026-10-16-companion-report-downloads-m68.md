## Recommended smallest useful workflow

1. Owner asks the companion to save `reports/summary.md` or `reports/ledger.csv` using its existing explicit file-write grant and approvals.
2. Owner opens **Files**, refreshes, selects that file, and chooses **Download current file**.
3. The authenticated SDK fetches bounded original bytes; the browser saves the selected basename. The file stays in the workspace unchanged.

**Choose Files-only for M68.** It closes an actual delivery gap with an existing owner selection and no artifact store, output-registration tool, transcript schema or Markdown change. A chat output button would require a trusted recorded successful-write/path binding and authenticated UI callback; model Markdown alone cannot establish that binding. Defer that separate convenience until a concrete need justifies it. Never make arbitrary assistant links trigger file reads/downloads automatically.

## Proposed interface and limits to bind

- New owner read route: `GET /api/workspace/file/download?path=<encoded relative path>`; use existing `local_owner.authorize_read`, strict query decoding, error handling and `Cache-Control: no-store` on success and failure.
- Only `.txt`, `.md`, `.csv` in this first report-delivery scope, case-insensitive. No document conversion, archives, HTML execution or broader binary browser. Download need not depend on successful/truncated preview; the server validates the full captured file independently.
- Path: 1–1,024 UTF-8 bytes, relative forward-slash components; reject controls, absolute/UNC/drive/ADS paths, dot/parent/empty components and backslashes. Reapply the existing Files exclusions to every path component, hidden entries and credential-field text, rather than trusting listing membership or filename extension.
- Reuse held nofollow/nonblocking regular-file reads. M67 `tools/workspace_bytes.rs::read_file_snapshot(relative,max)` supplies bounded opened-handle capture; retain the Files page's stricter hidden/name/content policy as well. A small shared private helper inside `routes/workspace_files.rs` may factor those existing checks; no broad filesystem refactor. Preserve current ordinary hard-link semantics and make no hard-link isolation claim.
- Reuse the existing 1 MiB text attachment ceiling as the proposed download limit; read at most max+1, refuse oversized data rather than truncate. Validate complete UTF-8 and existing allowed control characters; scan the whole admitted text for existing credential markers. Return captured **raw bytes**, preserving BOM, Unicode, CRLF, commas and empty files exactly.
- Response: `application/octet-stream`, safe `Content-Disposition: attachment` basename, `X-Content-Type-Options: nosniff`, exact `Content-Length`, no cache. Construct headers through safe encoding; never interpolate raw path text into headers. No capability token, persisted copy, upload record, file mutation or public sharing.
- Semantics: this downloads a bounded snapshot captured when clicked, not an immutable version of an earlier preview. A file changed since listing may produce current bytes or bounded refusal; do not claim same-preview/hash freshness. Root decides whether a later exact-preview download requires a separate digest contract.
- Bound concurrent physical reads using M67's existing `attachments/documents/source_read.rs::read_retained` four-lease/no-queue helper, with a finite deadline. Cancellation/disconnect must not release physical read capacity while blocking work survives. No parser/worker/model invocation.
- SDK: `WorkspaceClient.downloadFile(path,{signal?}): Promise<Blob>` plus `daemon.downloadWorkspaceFile(...)`. Reuse `DaemonClient.requestBoundedBlob` for a strict decoded 1 MiB ceiling and octet-stream type; accommodate valid zero-byte files without changing existing default voice/body requirements. Keep existing workspace DTOs unchanged unless an actual metadata need appears.
- Web: a properly labeled button for the owner-selected supported path, disabled while offline/downloading; separate download error and retry from preview state. Use the authenticated SDK, not a raw route anchor that omits configured owner headers. Reuse the existing attachment Blob/object-URL download pattern with abort, stale selection/unmount fencing and URL cleanup. Replace the truncated-preview local-open advice with the actual bounded-download option where available.

## Top five risks for root rulings

1. **File authority/privacy:** a new byte route must retain authenticated Files browsing exclusions and safe component opening; a listed name or assistant link cannot authorize an arbitrary filesystem read.
2. **Exact bytes versus preview:** downloading a truncated preview would corrupt reports; returning current bytes must not be advertised as an immutable earlier version. Credential scanning must cover the full bounded snapshot and remain a heuristic, not a secrecy guarantee.
3. **Resource ownership:** cancellation, slow files and repeated clicks must preserve bounded physical read leases; browser/SDK body limits must match the server and allow legitimate empty output without relaxing unrelated consumers.
4. **Download lifecycle and headers:** raw filenames cannot enter headers, HTML must not execute, stale responses cannot download a newly selected file, and every object URL must retire.
5. **Scope inflation:** exact untrusted CSV/Markdown delivery does not establish formula safety in external spreadsheet apps, report correctness, persistent artifact identity, public sharing or chat-output linking. Keep byte delivery separate from those claims.
