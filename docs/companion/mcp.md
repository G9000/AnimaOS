# External tools and agent permissions

## Set up a connection from chat

In a direct owner web/API chat, Anima can offer to configure MCP before any server is saved. Paste a **secret-free** server definition or give the server URL and ask Anima to set it up for the current agent. The native `manage_mcp` tool can list, configure, enable/disable, connect, discover, review, grant/revoke, disconnect, and remove the same connections shown in Connectors. It follows the existing Exec approval policy and records native action receipts.

For example: “Connect my project MCP at `https://project.example/mcp` and let this agent use its project-reading tools.” Anima saves a disabled definition, explicitly enables and connects it, and validates discovery. Free exposes validated tools automatically; Strict requires exact review and grants. Custom follows its execution setting: Allow exposes tools automatically, Ask requires review/grants and call approval, and Deny blocks MCP tools. Saving is not a successful connection test; discovery makes no tool calls. Newly connected/granted tools enter the next owner message's tool catalog. Configuration, reviews, and grants survive chats and restarts; after a restart, ask Anima to reconnect the saved connection before using it.

Configuration accepts one JSON server definition, optionally under `mcpServers`, `mcp_servers`, or `mcp.servers`. Supported definitions contain a Streamable HTTP `url` (or `endpoint`) or a trusted absolute Windows `.exe` `command` (or `executable`) with literal `args`. Unsupported options are rejected rather than silently removed. Existing limits below still apply, including no authentication fields in chat definitions, environment/cwd settings, shell/package launchers, arbitrary headers, or automatic reconnect. Start OAuth sign-in from the owner connection card.

Enter Bearer tokens for HTTPS or local loopback HTTP only through the existing **Connectors → MCP** password control. Do not paste tokens or passwords into chat: the original message and model history remain part of the conversation. Invalid setup arguments are omitted from live cards and rejected before approval or action-receipt admission. MCP setup is unavailable to helpers, delegated/peer requests, connector messages, jobs, and system follow-ups. The host rechecks owner-run authority after transaction waits and before admitting a save or connection; an already admitted operation retains owned completion and durability settlement.

An ordinary Anima agent can use MCP tools through Streamable HTTP with optional Bearer or OAuth authentication, or an explicitly started trusted local Windows process. Both use the official Rust SDK, fixed `2025-11-25` protocol and the same agent permissions, Exec approval and action receipts. Saving, listing or restoring a connection starts no transport. Discovery and review make no tool calls. Trusted Windows processes and reviewed community bundles have scoped local acceptance.

In review mode, the owner separately adds an exact reviewed alias to the agent's existing tool grants. Automatic access remains live and transient: it never writes reviews or grants. Switching to Strict or Custom Ask immediately requires actual saved reviews/grants, and Deny blocks access even when old grants exist. Mode/policy changes fence captured dispatch stamps, including a switch back to Free or a failed-save rollback. Every external tool uses the existing Exec approval category; server hints cannot lower its classification. Helpers inherit no MCP grants. The native dispatcher captures the exact descriptor, live connection generation and grant epoch before approval, then rechecks current policy and authority before dispatch and before accepting the result.

## Owner API

All operations are scoped to one existing ordinary agent at `/api/agents/{agent_id}/mcp-connections`. They use the existing local-owner authorization and return `Cache-Control: no-store`.

| Operation                  | Request                                                             | Result                                                                       |
| -------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| GET collection             | none                                                                | Own saved configuration and current runtime state                            |
| POST collection            | `label` and exactly one of `endpoint` or `stdio: {executable,args}` | Disabled version-one connection; no endpoint/process start                   |
| GET connection             | none                                                                | One own connection                                                           |
| PATCH connection           | `expectedVersion` and `label`, `enabled`, or HTTP `endpoint`        | Saved compare-and-swap edit; local launch is immutable                       |
| POST connection/connect    | `expectedVersion`                                                   | Initialize and complete bounded discovery                                    |
| POST connection/discover   | `expectedVersion`                                                   | Refresh current connection discovery                                         |
| POST connection/review     | `expectedVersion`, `discoveryId`, `descriptorDigest`                | Save one exact reviewed descriptor; no grant                                 |
| POST connection/disconnect | `expectedVersion`                                                   | Retire runtime transport; keep reviewed metadata and grants                  |
| DELETE connection          | `expectedVersion`                                                   | Save removal and remove only this connection's aliases from the owner grants |

Unknown fields, explicit null patch fields and empty patches are rejected. Endpoints allow HTTPS or local loopback HTTP (`localhost`/`127.0.0.1`/`::1`), without user information, query strings, fragments, redirects or ambient proxy use. A static Bearer credential is supported for HTTPS and local loopback HTTP Streamable HTTP connections. `localhost` is dialed using only fixed IPv4/IPv6 loopback addresses, without DNS or hosts-file lookup; other HTTP hostnames and addresses are rejected. OAuth browser sign-in and refresh are supported as described below. Arbitrary headers, shell command strings, environment/cwd settings and package installation remain unsupported.

Aliases contain the connection UUID and a descriptor-digest prefix. The full immutable digest is checked as well; a collision is rejected. Changed remote schemas/descriptions produce a new alias requiring review/grant in review mode, or available on the next turn in automatic mode. Endpoint or enabled edits retire live discovery; a label-only edit keeps discovery while advancing the saved version. Old reviews remain dormant when their exact descriptor is absent.

## Trusted local Windows processes

Choose Local process in Connectors, enter an installed absolute `.exe` path and an ordered argument vector, and confirm trust in that exact program/arguments. Saving stays disabled. Enable connection saves configuration; Start local server explicitly launches it. Each editor line is one literal argument: spaces/quotes have no shell meaning, untouched empty text means no arguments, and Pass one empty argument explicitly represents `[""]`. Changing launch input clears the trust choice. Saved executable/arguments cannot be edited; remove the connection and save a new one. Label/enabled edits remain available.

The API rejects missing/both transport inputs, explicit nulls, unknown fields, relative/empty executable values, control characters and known shell/package-manager launchers. Bounds are 2,048 UTF-8 bytes for the executable, 32 arguments, 2,048 bytes each and 16 KiB combined executable/argument content. Direct spawning clears inherited environment except fixed `SystemRoot`/`WINDIR` and uses a daemon-owned private TempDir working directory. No PATH search, shell interpolation, env map, cwd override, install/update or ambient provider configuration is supported. These controls do not sandbox the trusted executable.

Execution is Windows-only because whole-job descendant exit must be witnessed. Other hosts return unavailable before executable lookup, reservation or spawn. Existing HTTP connections remain portable. Public views add `transport: streamableHttp|stdio` and `stdio: null|{executable,args}`; `endpoint` stays a string and is empty for stdio. Durable HTTP rows retain their previous shape.

## Limits and recovery

- Four connections across the workspace; 32 durable reviews per connection, including dormant reviews.
- Five seconds for initialization plus complete first discovery; at most four pages and 64 candidate tools.
- Twenty seconds for one call, including queueing; one physical call per connection, two globally and at most four queued callers.
- Aggregate raw wire budget 256 KiB, individual JSON/SSE event 64 KiB, including raw comments and progress traffic.
- Reviewed descriptor/schema pair and arguments each 16 KiB, depth 16 and 1,024 nodes. Schemas use explicit Draft 2020-12, acyclic local `$defs` references and safe numeric values.
- Final model evidence envelope at most 16 KiB and 16 text blocks. Unsupported blocks and shortened content are explicitly marked. Returned text is external evidence with connection, generation, alias and digest provenance.

There is no automatic retry, reconnect, protocol fallback, stale discovery cache or additional model lookup. A timeout, Stop or revocation cannot prove that a remote effect was undone. A retired physical call keeps its slot until owned cleanup joins. Unknown cleanup retains its quarantine; shutdown can report unsettled effects without reusing the slot.

The four configured connections and global call/queue limits are shared by HTTP and stdio. A cached factory also retains at most four stdio child leases, including startup, retirement and quarantine; deleted configuration cannot free an unjoined child. Stdout is bounded before SDK decoding to 64 KiB per JSON-RPC line and 256 KiB per owned operation, with a separate 256 KiB unsolicited idle allowance. Malformed/oversized/invalid output maps to static errors; stderr is continuously discarded and never enters model results or owner diagnostics. Stop, disconnect, disable, delete, shutdown and revocation retain physical resources until owned protocol/sends/readers and the Windows whole-job wait join; uncertainty remains quarantined.

Control-plane version 18 retains existing HTTP metadata/reviews/grants and adds optional immutable stdio launch records. Version-17 migration has an independent `.pre-mcp-stdio.bak`, preserving the earlier `.pre-mcp.bak` for version 16. Restart restores every transport disconnected, with no network/process start, automatic retry or reconnect. Only explicit connect and exact rediscovery can restore readiness. Candidate saves settle through the existing ordered control-plane path before shared publication. Precommit failure preserves old metadata; uncertain post-replacement durability retains the candidate fail-closed and reports unavailable.

## Owner console and grant settlement

The owner console provides a typed SDK client and an owner panel in Connectors. Owners can add or edit a connection, explicitly enable and connect it, and refresh discovery. The daemon returns `toolAccess: automatic|review|denied` from the current agent policy. The panel explains automatic access or a policy block; review mode offers exact candidate review and separate grant/revoke controls. The panel displays saved configuration, review state, readiness and permission separately. It does not contact endpoints on mount, retry mutations, or provide a button to invoke a remote tool. Settings and MCP changes continue to use the existing agent grant list; ordinary unrelated Settings edits preserve MCP aliases, while choosing a standard profile remains an explicit whole-list replacement.

Granting or revoking one alias uses `PATCH /api/agents/{agent_id}/mcp-connections/{connection_id}/grants/{alias}` with `{expectedVersion,descriptorDigest,granted}`. The response is `{connection,granted,toolNames}`. The server checks the owner, current connection version and exact full digest of the reviewed alias, then changes only that alias in the current agent configuration. An effective change increments that connection's version and invalidates old dispatch stamps; an identical desired state is a checked no-op that preserves the version and `None` versus `Some([])` tool-list state. It never calls the remote server. Stale requests return a conflict for explicit refresh and reconfirmation.

Grant candidates save before publication through the ordered control-plane path. Precommit failure leaves the prior grant and record in place. Durability uncertainty publishes the observed candidate fail-closed, retires the affected transport and returns unavailable; the UI must not describe this as rollback or resubmit automatically. A bounded acknowledgement merges only aliases from an older snapshot, preserving current-version owner edits, native grants and other connections. Revoking an alias fences active dispatch; an already-running physical call keeps its slot until cleanup finishes, and revocation cannot prove that a remote effect was undone.

Broader MCP interoperability remains partial. Windows stdio, declarative MCP/skill bundle installation/update, and owner-managed static Bearer credentials for HTTPS and loopback HTTP are implemented with scoped local acceptance. Non-Windows stdio, arbitrary headers, compiled connector contributions and selected real-server acceptance remain open. OAuth public-client sign-in and refresh now have synthetic acceptance below. These checks do not establish arbitrary-server safety, useful task quality or whole Hermes parity. The implementation reuses the official Rust MCP SDK and maintained process-wrap ownership; public Hermes source informed lifecycle comparison, without importing private profiles or copying its Python runtime. See the [bundle guide](community-bundles.md) for exact owner bindings, pending adoption, lifecycle CAS, global skill scope and cleanup limits.

### Account sign-in with OAuth

For an HTTP server, choose **Sign in** on its connection card. Complete the provider's consent page in the browser, then return to AnimaOS. **Continue sign-in in browser** is available if the browser blocks the new tab. The owner panel checks local account status and polls only a pending attempt; opening the panel never starts sign-in or contacts a provider. An enabled connection initializes and discovers tools after a successful sign-in. A disabled connection stays disabled. Account authentication follows the agent's existing tool policy and never writes tool grants.

The server must advertise OAuth protected-resource metadata, authorization-server metadata and PKCE S256 support. Its authorization server must also advertise RFC 9207 issuer responses (`authorization_response_iss_parameter_supported: true`) and return the exact issuer in every success/error callback. AnimaOS intentionally rejects older servers that omit issuer identification to prevent authorization-server mix-up attacks. AnimaOS uses a public native client: advertised dynamic registration works without a client ID; providers requiring pre-registration can use **Advanced sign-in settings → Client ID (optional)**. The provider must support public clients without a client secret and numeric loopback redirects using an ephemeral port and the fixed path `/oauth/mcp/callback` (`http://127.0.0.1:{port}/oauth/mcp/callback`). Hosted client metadata documents, confidential app secrets, device-code grants and automatic scope escalation are not included. This flow uses the browser on the same computer as the daemon.

**Cancel sign-in** invalidates the pending attempt. **Disconnect server** stops the transport and keeps the saved account. **Sign out** stops the connection and removes local OAuth credentials; advertised provider revocation is best effort and does not claim to sign out other devices or browser sessions. An expired/rejected refresh grant requires another sign-in. Authentication failures never replay a tool call. Editing a server URL clears its endpoint-bound credential. Changing credentials, deleting a connection, stopping the daemon and changing the owner agent fence old callbacks and refresh work.

Access and refresh tokens stay in the OS credential vault, bound to the connection and exact normalized endpoint. Only an opaque credential reference is persisted outside it; owner responses expose `hasOAuthCredential` as a saved-reference flag that does not establish remote account health. Windows vault payloads use bounded chunks and immutable generations so token rotation can be saved before dispatch. A failed or uncertain credential write blocks use and requires review. Restart restores account references with every transport disconnected and makes no automatic provider requests.

The reusable `anima-mcp-oauth` crate wraps the official Rust MCP SDK authorization flow. It validates protected-resource/issuer discovery, audience, PKCE and one-use callback state, and denies redirects, ambient proxies and remote discovery into local/private networks. Local MCP resources may use fixed loopback addresses. Requests and responses have byte/time limits; attempts expire after ten minutes. Codes, tokens and provider response bodies are excluded from diagnostics and the browser callback page. Control-plane version 31 adds optional OAuth references and preserves version-30 JSON bytes in a separate `.pre-mcp-oauth.bak` before upgrade.

All account routes use the existing owner authorization and `Cache-Control: no-store`, under `/api/agents/{agent_id}/mcp-connections/{connection_id}`:

| Operation | Request | Result |
| --- | --- | --- |
| POST oauth/start | `expectedVersion`, optional public `clientId` | `authorizationUrl`, `attemptId`, `expiresAt` (Unix seconds) |
| GET oauth/status | none | `state`, optional `attemptId`, `expiresAt`, static `error` |
| POST oauth/cancel | `expectedVersion`, `attemptId` | Connection after canceling that exact attempt |
| DELETE oauth | `expectedVersion` | Connection after local sign-out |

Account states are `signed_out`, `pending`, `connected`, `needs_sign_in` and `failed`. `connected` describes saved account authentication; the separate connection `state` still determines MCP transport readiness. SDK methods are `startOAuth`, `getOAuthStatus`, `cancelOAuth` and `signOutOAuth`. Mutations are versioned and never automatically retried. Synthetic validation covers discovery, callback/PKCE/issuer checks, refresh rotation, vault capacity, lifecycle fencing and account UI; real-provider consent and actual OS-vault acceptance remain separate live checks.

See the [OAuth design](../superpowers/specs/2026-10-27-mcp-oauth-design.md) and [implementation and validation plan](../superpowers/plans/2026-10-27-mcp-oauth.md).

### Owner-managed Bearer credentials

Bundle removal deletes credential slots only for its exact owned removal set, including its dormant predecessors. Disable and retained rows outside the removal set keep their slots. If any deletion fails or is uncertain, removal intent and all row references remain for review; already completed deletions are not rolled back.

On an HTTPS or local loopback HTTP Streamable HTTP connection, an owner can explicitly save or replace a static Bearer token, or clear it. The password is entered only in the owner control; connection list/get exposes `hasBearerCredential` as a saved-reference indicator. It does not read the OS vault or establish that the credential is available, accepted, or that the server is healthy. The token is stored in the OS credential vault and bound to that connection's exact normalized endpoint. Editing the endpoint clears the binding, so enter the token again for the new endpoint.

Credential changes retire and join the active connection before mutation. A failed or uncertain result requires the owner to refresh the connection view and decide whether to re-enter or clear the credential; the console does not retry, reconnect, or replay a mutation. Explicit connect/discovery remains separate from credential changes; review-mode grants remain separate owner actions. Stdio and unauthenticated HTTP connections are unchanged; arbitrary headers and the unsupported GET event-stream path remain unavailable. OAuth account sign-in is a separate credential option described below. Earlier native and UI acceptance used synthetic credentials and local TLS.
