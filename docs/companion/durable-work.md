# Durable companion workflows

Anima supports reviewed recovery, side questions, durable structured questions, completion checks, reusable procedure authoring, owner event automations and programmatic native tool chains through the existing Rust daemon. The detailed owner guide is [Companion workflows](../../apps/docs/src/content/docs/companion-workflows.mdx).

See [Learning and context quality](learning-context-quality.md) for opt-in evaluation before promotion, saved compaction checkpoints, request-copy pruning and file-version completion evidence.

## Saved workflows

Enable **Permissions -> Allow workflows in chat**, save, then ask the companion to create a saved workflow with task, approval, and question steps. The agent's workflows appear inside ordinary web chat. Approve with **Approve checkpoint**, or enter **Your answer** and choose **Submit answer** on the workflow card. Decisions go directly through the owner API; ordinary composer messages do not approve or answer checkpoints. The chat section is agent-scoped and includes workflows created elsewhere. Turning off the grant prevents model creation/listing while leaving the owner's saved workflow controls available.

Open **Work -> Workflows**, choose a companion, and create an ordered sequence of tasks, approval checkpoints, and questions. For example: gather report facts -> approve the facts -> choose an audience -> write the report. Each task uses the existing durable job runner; its saved output becomes bounded reference data for later tasks. Approval and input checkpoints survive restart. Continue the saved workflow to advance from that point; earlier completed steps keep their results and are not run again.

A failed, interrupted, stopped, uncertain, or truncated task pauses for owner review. Inspect its linked job and any external effects. **Retry** needs an explicit acknowledgement and creates a fresh task attempt; **record a verified result** lets the owner supply the result after checking the effects. Neither action replays earlier successful steps. Cancellation prevents new steps and requests the existing stop control for an active task; it cannot undo effects that already occurred. Each task allows at most three attempts, with one attempt per linked job. Generic job controls cannot bypass workflow decisions.

Workflows require persistent control-plane storage. Retained history is bounded to 50 workflows, 16 steps each, 32 KiB of definition text, 8 KiB per prompt/answer, and 64 KiB per task result. Existing global job history and execution limits also apply. Temporary slot exhaustion waits; retained job-history exhaustion requires review. Exact repeated creation keys or checkpoint decisions are idempotent, and changed input under the same key/revision conflicts. The SDK exposes `client.workflows`; explicitly granted ordinary chat runs can use `create_workflow` and `list_workflows`. Only owner API/UI actions can continue checkpoints.

This is a sequential agent-task workflow. Each task can call the configured model and its permitted tools; it is not a zero-model-call script pipeline. Task runs do not delegate or spawn helpers. A workflow checkpoint does not grant tools, approve a separate email draft, or establish that every business outcome is correct. Nothing is automatically scheduled. Snapshot version 24 adds workflow progress and keeps an exact `.pre-workflows.bak` copy when upgrading a version-23 JSON store.

- Interrupted owner tasks offer **Review interrupted work**, followed by a linked continuation with current permissions, original attachments and the selected skill. Repeated requests return the same continuation; each chain permits three attempts. Unknown effects require review. Pending questions pin their source; ordinary run-history retention otherwise applies.
- `/btw <question>` answers from a bounded conversation and current-task snapshot while work continues, without tools or transcript mutation. Side answers remain separate from saved task history.
- The `clarify` tool saves structured questions before showing them. A saved answer wakes a live task; after restart, the owner answers then explicitly continues through recovery. Owner stop cancels pending requests. Only ordinary web chat runs can open structured questions.
- Completion evidence checks remain bounded. Six fresh identical failures force a tools-disabled final explanation; successful polling stays allowed. Runaway repeated text is stopped with an incomplete marker, preserving reported usage.
- State format 23 has an exact independent `.pre-companion-interaction.bak` upgrade backup. No normal profile or data store was reset for this work.

- Send `/learn <workflow or source>` to gather sources and propose a skill in an ordinary task. Bare `/learn` uses the conversation. Current grants and skill controls still apply: Strict and Custom keep a review draft; Free can activate it with an undo entry. Skills contain a bounded `SKILL.md` and reviewed supporting files; scripts remain inert until execution is authorized.
- Create an automation with `{ "type": "event", "topic": "files.changed" }`, then publish through the owner-authorized `POST /api/agents/{agentId}/automation-events` endpoint or `client.automations.emitEvent`. Local file or webhook adapters can publish events; no filesystem watcher or public unauthenticated webhook is started.
- Committed ordinary outcomes, including owner-reviewed recovery attempts, publish `task.completed` and `task.failed`. Pre-admission/start refusals, interrupted/cancelled work, schedules, helpers and other system followups do not publish outcomes. Event payloads are untrusted source data. Existing active hours, approvals, delivery targets and histories apply.
- Event identities remain durable for the lifetime of their schedule, without eviction. At most 64 occurrences may wait and 256 identities may be retained across live automations. New events fail with a visible capacity error when full; exact retries remain duplicates. Deleting an automation releases its identities. Reusing a retained key with changed payload returns a conflict. Payloads are JSON objects bounded to 8 KiB and limited nesting. A native outcome that cannot fit is logged without failing its original task.
- Programmatic chains require Windows, an explicit absolute Python 3.10+ interpreter in `ANIMAOS_RS_TOOL_RPC_PYTHON_PATH`, shell access and a separate `execute_code` grant. Configuration status is available in access settings. Programs import native functions from `anima_tools`, use native keyword arguments and start fresh each time. Native calls retain their own grants, approvals and receipts; the outer program retains cancellation, deadlines and owned process cleanup. Local Python has the operating-system access of the daemon user.

Deterministic scripted tests and synthetic local tool execution are validation evidence for these boundaries. They do not establish live model, external connector, webhook provider or other-platform acceptance.
