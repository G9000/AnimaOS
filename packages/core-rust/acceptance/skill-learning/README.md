# Live skill-learning acceptance

Run `node tools/skill-learning-acceptance.mjs help` from the repository root for phases. The phase sequence is also in the script header. `prepare --binary PATH` copies a freshly built daemon into a new dedicated directory under `.tmp`; it does not launch it. No phase compiles Rust.

`baseline`, `correction`, and `fresh` each submit one real-provider run. `review` only observes the automatic background reviewer. It waits through the handoff between a completed review and its source-linked approved draft, active package, and durable undo ledger. A pending run/review wait ends after 55 seconds and prints the command to observe the same work again. A completed review whose handoff is still absent after the bounded wait fails acceptance. An uncertain admission is retained and never automatically resubmitted. Failed acceptance is reported without repairing the learned skill.

The bad initial procedure deliberately adds positive refund amounts. The baseline oracle requires that incorrect result (16500 cents). The owner correction specifies refund subtraction; its exact expected result is 12500 cents. The independently authored fresh fixture has different sale and refund sums and expects 14975 cents. Each output is compact JSON with exact keys, order, values, and bytes. Supporting skill files must survive the background revision and undo.

The fresh agent receives equivalent model configuration and only `load_skill`, `read_file`, and `write_file`. It begins with empty canonical/core memory and an empty session. Its user prompt only names the reconciliation task and fixture. Afterward, only its own runtime output journal created at or after run completion is allowed; facts, reflections, and core-memory instructions remain absent. Evidence must show the native tool result containing the revised skill body and a per-version observation matching its exact agent/session/run/package hash. Strict baseline/fresh writes are allowed once only for their declared output file. No foreground skill authoring or memory tools are granted.

`checkpoint` / `stop` / `restart` / `reload` separately check settled skill, usage, review, draft, ledger, agent, and memory persistence. `undo` restores the initial body, supporting files, and approved hash through the existing owner route. `proof` succeeds only after all required phases and both owned daemon processes have stopped.

On Windows, `process-identity.js` uses the built-in Windows Script Host for a read-only PID/executable/creation-time check. The Codex filesystem sandbox can deny Script Host settings, so run the harness outside that sandbox through the normal tool approval mechanism. Every stop checks the recorded process identity and targets only that PID. Daemon output is discarded to avoid persisting provider diagnostics containing credentials. The only credential read from the repository `.env` is passed in the owned daemon's environment; `.env` and owner profiles are never copied into acceptance evidence.

`self-test` checks the fixture oracles, malformed fixture rejection, secret redaction, and process identity. It makes no provider calls and starts no daemon. Passing this offline check does not establish live learning acceptance.
