## Resume a saved workflow

In **Permissions**, turn on **Allow workflows in chat** and save. This explicitly grants `create_workflow` and `list_workflows` to the selected companion without enabling extra task tools. Then ask in ordinary web chat:

> Create a saved workflow called “Reviewed report”: summarize the selected notes, pause for my approval, ask who the audience is, then draft the report using the saved summary and my answer.

The **Workflows** section inside chat shows the selected companion's saved workflows, including workflows created elsewhere. Use **Approve checkpoint** on its card, or enter **Your answer** and choose **Submit answer**. These are direct owner decisions; simply typing “approved” into the regular message composer does not resume a checkpoint. Creation may still require the companion's existing execution approval. Completed and cancelled cards collapse in chat and can be expanded to inspect their saved results and decisions. Disabling chat workflow permission prevents model creation/listing; the owner can still inspect and continue previously saved workflows using the cards.

Open **Work -> Workflows**, choose a companion, and add an ordered sequence of **Task**, **Approval**, and **Question** steps. A report workflow might gather facts, wait for your approval, ask who the audience is, and then write the report.

Each task runs as a durable job. Anima saves its result before admitting the next step. Approval and question checkpoints survive restart: approve or answer the displayed checkpoint to continue the existing workflow. Earlier successful steps stay completed and are not run again.

When a task fails, stops, has an uncertain effect, or lacks a complete saved result, the workflow waits for review. Inspect its linked job and verify any effects. You can explicitly acknowledge the uncertainty and retry that step, or record a verified result yourself to continue. A step allows at most three attempts. Original jobs and their receipts remain available; generic job retry controls cannot replay a workflow attempt.

Cancel stops future steps and requests the current task's existing stop control. It does not roll back effects that already happened. Workflow approval leaves the companion's tool permissions and separate connector approvals in place. Workflow task runs do not delegate or spawn helpers.

An already owner-authorized SDK client can also start a workflow:

```ts
const workflow = await client.workflows.create(agentId, {
  title: 'Reviewed weekly report',
  requestKey: 'weekly-report-2026-10-21',
  steps: [
    { id: 'research', title: 'Gather facts', kind: 'task', prompt: 'Read the selected workspace notes and summarize the weekly facts.' },
    { id: 'review', title: 'Review facts', kind: 'approval', prompt: 'Approve the saved facts before drafting the report.' },
    { id: 'audience', title: 'Choose audience', kind: 'input', prompt: 'Who should this report be written for?' },
    { id: 'draft', title: 'Draft report', kind: 'task', prompt: 'Write the report for the chosen audience using the approved facts.' },
  ],
});

const current = await client.workflows.get(agentId, workflow.id);
if (current.status === 'awaiting_approval') {
  await client.workflows.resume(agentId, current.id, {
    revision: current.revision,
    action: 'approve',
  });
}
```

Reuse the original creation key and exact decision payload after an uncertain response. A repeated decision is a no-op; changed input under an already used key or revision conflicts. The web controls retain unresolved requests for explicit retry. The `create_workflow` and `list_workflows` tools require explicit grants and an ordinary companion chat; models cannot approve, answer, retry, or resolve checkpoints themselves.

Persistent storage is required. Limits are 50 retained workflows, 16 steps each, 32 KiB total definition text, 8 KiB per prompt or answer, and 64 KiB per saved task output. The existing 200-job history and eight active-job limits still apply. A pending task waits for a slot; exhausted retained job history pauses for review. These are sequential model-backed tasks, rather than a zero-model-call native tool script, and creating a workflow does not schedule recurring work.

## Continue interrupted work

An interrupted or failed owner task offers **Review interrupted work** below its recorded actions. Inspect those actions, especially any unknown outcome, acknowledge the review, then choose **Continue remaining work**. Anima starts a linked attempt in the same chat using current permissions and the original attachments and skill selection. It checks saved progress before acting; the original run and its action evidence stay available.

Repeated clicks return the same saved continuation, including after restart. Each chain allows at most three continuations. Work that was explicitly stopped, connector tasks, helpers and background jobs use their existing controls instead. Ordinary run-history retention still applies; unanswered questions keep their source available for recovery.

If a send or other external effect is uncertain, check the destination before authorizing continuation. A successful tool receipt alone cannot establish that the entire task succeeded. Anima never automatically replays an interrupted task.

## Ask while Anima works

Use `/btw <question>` in an existing web chat, or type it and choose **Ask side question**. The answer appears separately while the main task continues. It uses a bounded snapshot of the conversation, the active owner request and recorded progress; it does not use tools, change the main task or add a new task to its queue. The snapshot can be incomplete, and the side answer is not saved into the main transcript.

## Answer a question from Anima

Anima can show a question card with choices, multiple selections where requested, and a free-text answer. Choose **Submit answers** to save your response and let the waiting task continue. Answering grants no additional tool permissions.

Pending questions survive daemon restart. Submit the saved answers, then use the interrupted task's recovery review to continue; saving an answer after restart does not replay the old task. Owner stop cancels pending questions. Structured question cards are currently supported in ordinary web chats; connector and helper runs cannot open an unanswerable card.

## Completion and loop protection

Anima reviews settled file reads, checks and saved tasks before finishing. Repeated identical failures eventually lead to a final explanation with tools disabled. Repeated successful polling remains possible. Long runaway text is cut off and marked incomplete; text streamed before detection can remain visible. These checks help expose unfinished work; they are not a proof that every requested outcome is correct.

## Existing workspace data

The durable state format is version 25. On upgrade from version 24, the daemon preserves the exact JSON file as `.pre-workflow-templates.bak`. Version-23 upgrades keep their separate `.pre-workflows.bak` backup. Version-22 upgrades keep their separate `.pre-companion-interaction.bak` backup; older backups remain separate. No reset or data deletion is needed. Keep your configured persistent store and workspace path across restart.

## Learn a reusable procedure

Send `/learn <workflow or source>` in a chat. Include every source and constraint, for example:

```text
/learn docs/deployment.md and the workflow we just finished. Focus on rollback; skip production credentials.
```

Bare `/learn` uses the current conversation. This starts an ordinary task with the agent's current file, web and skill permissions. It gathers the sources and uses `propose_skill`; Strict and Custom leave a draft for review, while Free can activate it through the existing skill controls and keep an undo entry. The chat and Skills page show the actual result. Skills currently use one bounded `SKILL.md`; a multi-file book or document ingestion engine is not included.

## React to an event

Choose **Run when an event arrives** in the automation editor, or create a trigger through an already owner-authorized SDK client:

```ts
const automation = await client.automations.create(agentId, {
  name: 'Review changed files',
  prompt:
    'Review the changed file in the event payload and explain what needs attention.',
  trigger: { type: 'event', topic: 'files.changed' },
});

await client.automations.emitEvent(agentId, {
  eventId: 'file-revision-42',
  topic: 'files.changed',
  payload: { path: 'notes.txt' },
});
```

The owner endpoint is `POST /api/agents/{agentId}/automation-events`. It uses the same local owner authorization as automation changes: an approved local browser origin, or the configured local admin bearer token for a local adapter. It does not expose a public unauthenticated webhook. A file-change or webhook adapter can publish through this endpoint; Anima does not start a filesystem watcher.

Committed ordinary task outcomes, including reviewed recovery attempts, publish `task.completed` and `task.failed` for the task's agent. Pre-admission and start refusals, interrupted or cancelled work, schedules, helpers and other system followups do not publish these events. This prevents an automation from triggering itself through its own completion. Event payloads are source data; they do not grant tools, permissions or instructions. Existing active hours, approval rules, delivery targets and run history apply. Companion-created event automations run at least five minutes apart.

Reuse an `eventId` for retries of the same event. A different payload under a retained ID returns `409`. The daemon saves accepted occurrences before execution and retains their identities for the lifetime of the schedule. It admits at most 64 pending occurrences and 256 retained occurrences across live automations; new events return `429` when capacity is full, while exact retries remain duplicates. Deleting an automation releases its retained identities. Payloads must be JSON objects of at most 8 KiB, with bounded nesting. Native outcomes that cannot fit are logged and do not fail the original task. An interrupted claimed occurrence requires review and is not automatically replayed after restart.

## Chain native tools in a Python program

On Windows, explicitly select an installed Python 3.10 or newer interpreter before starting the daemon. Set `ANIMAOS_RS_TOOL_RPC_PYTHON_PATH` to its absolute executable path in that launch environment; restart the daemon after changing it. Anima does not discover an interpreter from personal profiles or install one automatically.

In the agent's access settings, choose shell access and enable **Allow programmatic tool chains**. This separately grants `execute_code`; each native tool also needs its own grant. The settings show whether the interpreter is configured. Configuration is not an execution health check.

The agent can then send a complete Python program to `execute_code`:

```python
from anima_tools import read_file, write_file

first = read_file(file_path="first.txt")
second = read_file(file_path="second.txt")
write_file(file_path="combined.txt", content=first + "\n" + second)
print("combined.txt was written")
```

Each call starts fresh; variables do not persist between programs. The generated `anima_tools` module includes only the currently granted subset of `web_search`, `web_fetch`, `read_file`, `write_file`, `glob`, `grep`, `edit_file`, `multi_edit` and `bash`. Native keyword arguments are unchanged. The outer program requires execution approval, and native calls keep their own approvals and durable receipts. Local Python has the operating-system access of the daemon user. Cancellation, a five-minute deadline and owned process cleanup remain enforced; uncertain effects require review.


## Reuse a workflow template

Open **Reusable templates** in the chat's Workflows section or in **Work → Workflows**. Choose **New template**, or copy the steps of an existing workflow. Give it a slug, add named parameters and optional defaults, and use placeholders such as `${topic}` in titles or prompts. `$${topic}` keeps the placeholder as literal text. Parameter values are plain strings; they never evaluate code or expand environment variables.

Save the template, select it, enter its inputs, and choose **Run template**. Each start creates a separate workflow. Its template revision, resolved inputs, steps, results, and checkpoint decisions remain pinned even if you later edit or remove the template. Existing owner checkpoint controls still apply.

To create, inspect, and start templates by asking the companion, enable **Allow workflow templates in chat** in Permissions and save. This separately grants `save_workflow_template`, `list_workflow_templates`, and `run_workflow_template`. For example:

> Save a reusable template called “Reviewed brief” with slug reviewed-brief, a required topic parameter, and these steps: draft a short brief about the topic, wait for my approval, ask for the audience, then finish the brief. Use the template tools. Save it first; do not start it yet.

Then ask to run that template with a specific topic. Chat text does not approve a checkpoint: use **Approve checkpoint** or **Submit answer** on its saved run card. Disabling template permission prevents model saves, listings, and starts; owner controls remain available.

The owner SDK exposes `client.workflowTemplates.list/get/save/run/delete`. Save uses revision 0 for a new slug and the current revision for edits. Run uses `{ revision, requestKey, inputs }`. Reuse the exact request after an uncertain response. A fresh request key starts separate work. The web interface retains unconfirmed commands for **Retry exact template request**.

Limits are 25 retained templates across the store, including removed picker entries, 16 saved revisions each, 16 parameters, and the existing 16-step workflow bounds. Each input fits 8 KiB and all resolved inputs together fit 16 KiB. Removing a template retains its history and existing runs for consistent recovery; use another slug when revision history is full.

## Include supporting files in skills

The skill editor and chat skill proposals can include reviewed UTF-8 text files under `references/`, `templates/`, `scripts/`, `examples/`, or `assets/`. Use **Add supporting file** in the editor, enter its package-relative path and content, and save the package. A chat request can ask the companion to propose a skill with these files for review.

Review includes SKILL.md and every supporting file. The approved package hash pins all paths and bytes: modifying, adding, or removing a supporting file makes the skill unavailable until reviewed again. Existing single-file skills keep their original hashes. The package supports up to 32 supporting files, 64 KiB per file, and 512 KiB total. Path escapes, links, unsupported roots, and duplicate paths are rejected.

`load_skill({ name })` loads instructions and the file index. `load_skill({ name, filePath: 'references/guide.md' })` loads exactly one currently approved supporting file. Scripts are inert text; including or loading one does not execute it or grant shell permission. Skill proposals follow the current autonomy setting: review when required, or a saved ledger entry that the owner can undo under Free.

## Read a saved large tool result

When an available tool result exceeds 16 KiB, a configured durable host saves its exact JSON result privately and returns a compact preview with an opaque saved-result ID. Already bounded native management and search envelopes keep their structured handles and citation contracts. Expand that tool step in chat and choose **View saved result**. Read bounded pages with **Next page**, or choose **Download saved result** for the full stored payload. Reopening the chat retains the reference. A tool that already reported truncated output is marked incomplete; storage cannot recover bytes it never received.

Enable **Allow saved tool result reads** in Permissions to let the companion use `read_tool_result` for bounded retrieval by ID. Reads remain scoped to the current agent and workspace, recheck the live grant, and treat saved text as reference data. Owner viewing and downloading do not require this model permission. Storage never changes the original tool's success, error, cancellation, or uncertain-effect status.

Each artifact fits 4 MiB; the private store has a 128 MiB and 1024-file quota. Referenced artifacts are not automatically deleted. With a JSON control plane, the default directory is the control-plane filename plus `.tool-results`. For a Postgres control plane, configure an absolute private `ANIMAOS_RS_TOOL_RESULTS_DIR` for that profile. Ephemeral hosts do not retain tool results. A failed or unavailable save is reported without claiming the original output was retained.
