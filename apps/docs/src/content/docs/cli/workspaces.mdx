This page covers the CLI workflow that starts on disk rather than in the daemon: scaffold an agent workspace locally (or hand-write an agency `anima.yaml`), edit it like normal project files, then launch it against the host.

## Core Split

- `animaos create` is local. It writes files and does not require the daemon.
- `animaos launch` is daemon-backed. It reads `anima.yaml`, creates a runtime swarm in the host, and runs tasks through the daemon.

That split is the main reason the CLI is practical for real work: you can shape the workspace locally, review it, and only then execute it.

## Create a Workspace

```bash
# Interactive prompt for name and description
animaos create

# Single-agent workspace
animaos create agent medicine-helper \
  -d "Research medical literature and summarize risks clearly"
```

`create` makes no model call. It writes the workspace files from a template and records the provider in `anima.yaml`: the one you pass with `-p`, otherwise the first remote provider with credentials configured, otherwise `deterministic`.

| Flag | Default | Description |
|------|---------|-------------|
| `--kind` | — | `agent` |
| `-p, --provider` | `auto` | Provider recorded in the workspace. Supports `deterministic` and the daemon-facing provider family |
| `-m, --model` | `gpt-4o-mini` | Model recorded in the workspace |
| `-d, --description` | — | What the agent should do |
| `--system` | — | System prompt for the agent |
| `--api-key` | — | API key, used only to detect which provider is configured |

<Aside type="note">
  `create` only scaffolds a single agent. To run a multi-agent agency, write `anima.yaml` by hand (an `orchestrator` plus an `agents` list) and run `animaos launch` in that directory.
</Aside>

## Workspace Shape

The scaffolded workspace is designed to be edited by humans before launch:

```text
medicine-helper/
├── anima.yaml
├── org-chart.mmd
├── README.md
└── agents/
    └── medicine-helper/
        ├── profile.md
        ├── assets/
        └── memory/
```

The important files are:

- `anima.yaml` for runtime config
- `agents/*/profile.md` for human-readable role shaping
- `agents/*/memory/seed.json` for optional preloaded memories posted at launch time (add it by hand; `create` does not generate it)

## Launch a Workspace

```bash
cd medicine-helper

# TUI session
animaos launch

# One-shot task in the TUI workflow
animaos launch "Summarize the latest research"

# Plain-text mode
animaos launch --no-tui "Summarize the latest research"
```

`launch` is the best operator flow when you want the TUI, saved run history, and daemon-backed workspace execution.

| Flag | Default | Description |
|------|---------|-------------|
| `--api-key` | — | API key override for the current daemon-backed run |
| `--no-tui` | — | Disable Ink and use plain text |

<Aside type="tip">
  Use `launch` when you care about durable workspace structure, team composition, saved history, or the TUI. Use `run` only when you want a quick one-off result without creating a workspace first.
</Aside>

## Seed Memories

If the workspace contains `agents/<slug>/memory/seed.json`, the CLI can post those memories into the daemon before the agency starts running. That gives the launched team a useful local memory baseline without hardcoding those facts into the host.

This keeps agency memory bootstrap close to the workspace itself instead of hiding it in global daemon state.
