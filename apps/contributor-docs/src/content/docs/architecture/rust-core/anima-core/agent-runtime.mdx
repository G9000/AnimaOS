`AgentRuntime` is the stateful executor at the center of `anima-core`. It lives in `packages/core-rust/crates/anima-core/src/runtime.rs`, with run control, live frames, run deltas and failure guards in `runtime/`. It drives one task at a time through the loop below.

## Creating a Runtime

```rust
use anima_core::{AgentConfig, AgentRuntime};
use std::sync::Arc;

let config = AgentConfig {
    name: "researcher".into(),
    model: "gpt-4o".into(),
    provider: Some("openai".into()),
    bio: Some("You are a meticulous research assistant.".into()),
    lore: None,
    knowledge: None,
    topics: None,
    adjectives: None,
    style: None,
    system: None,
    tools: Some(vec![search_tool_descriptor]),
    plugins: None,
    settings: None,
    fallbacks: Vec::new(),
};

let mut runtime = AgentRuntime::new(config, Arc::new(my_model_adapter));
runtime.init();                                  // records the AgentSpawned event
runtime.register_provider(Arc::new(my_provider));
runtime.register_evaluator(Arc::new(my_evaluator));
runtime.set_database(Arc::new(my_db));           // optional step persistence
```

`AgentRuntime::new` assigns an agent id (`agent-N`, from an atomic counter; `new_with_id` takes your own), sets status `Idle`, and stores the config and adapter. No network call happens during construction. `AgentConfig` has no `Default` impl; the optional fields (`bio`, `lore`, `knowledge`, `topics`, `adjectives`, `style`, `provider`, `system`, `tools`, `plugins`, `settings`, `fallbacks`) must be spelled out.

## Run Entry Points

| Method | Behavior |
|--------|----------|
| `run(input)` | New room, no history, no tools. A tool call fails with `Unknown tool`. |
| `run_with_context(history, input)` | New room, with earlier messages. |
| `run_in_room_with_context(room, history, input)` | Host-chosen room. |
| `run_with_tools(input, execute_tool)` | New room, with a tool executor closure. |
| `run_with_context_and_tools(...)`, `run_in_room_with_context_and_tools(...)` | The general forms; the daemon uses the in-room one. |

`execute_tool` is `Fn(AgentState, Message, ToolCall) -> Future<Output = TaskResult<Content>>`. All variants return `TaskResult<Content>`.

## Builder-Style Hooks

| Setter | Purpose |
|--------|---------|
| `set_event_listener` | Synchronous callback for every `EngineEvent` |
| `set_run_observer` | Live, non-recorded `RunFrame`s (text deltas, tool cards) |
| `set_run_control` | `RunControl`: stop signal plus steering inbox |
| `set_run_id`, `set_persistence_agent_id` | Scope persisted tool-step keys to a host run |
| `set_agent_files` | Rendered `SOUL.md` / project instruction files for this run |
| `set_host_guidance` | Mandatory host-owned prompt text |
| `set_default_tool_iterations` | Tool-round budget when the agent's settings leave it unset |
| `set_providers`, `set_evaluators`, `set_database` | Bulk or optional collaborators |

## The Task Loop

```
run_in_room_with_context_and_tools(room, history, input, execute_tool)
│
├─ mark_running()                       status = Running; agent:started, task:started
├─ record the user message in the room  agent:message
│
└─ loop:
     ├─ stop checkpoint                 → finish as stopped
     ├─ drain the steering inbox        steered messages join as user messages
     ├─ build provider context          providers by priority; one snapshot per run
     ├─ build the system prompt
     ├─ ModelAdapter::stream(...)       frames forwarded to the RunObserver
     ├─ record usage                    agent:tokens
     └─ on the stop reason:
          End | MaxTokens  → run evaluators → Accept: complete
          │                                   Retry:  revise (max 2) and loop
          │                                   Abort:  fail with the reason
          ToolCall         → validate tools are configured
                             prepare steps (persistence, retry-key reuse)
                             run the batch in parallel (join_all)
                             record tool results, loop again
```

### System prompt

Built in this order, joined with blank lines:

1. If a host accepted a SOUL / identity file, its text. Otherwise, the legacy persona: `bio` (Who You Are), `lore` (Your Backstory), `adjectives` (Your Personality), `topics` (Your Expertise).
2. `knowledge` as a bullet list (What You Know). Always included.
3. Without an identity file: `style` (How You Communicate), then `system` (default `You are a helpful task agent.`).
4. Project context rendered from agent files.
5. Host guidance.
6. Provider output as `[provider_name]: text` lines under `## Context`.

### Providers

Providers run in descending `priority()` order (ties keep registration order). Each is called once per run and its text is reused for later model calls in the same run, unless the provider's `refresh_each_model_request()` returns true. A provider error fails the run with that error text.

### Tool rounds and the budget wrap-up

The round limit is `AgentSettings.max_tool_iterations`, else the host default set by `set_default_tool_iterations`, else `MAX_TOOL_ITERATIONS` (8). When the limit is reached the next model call is a **tool-free wrap-up**: tools are removed, retries are set to zero, and guidance tells the model to report completed and remaining work honestly. If that answer requests tools, is truncated or is empty, the run fails (`tool iteration limit exceeded`, `budget wrap-up was truncated`, `budget wrap-up returned empty text`). An accepted wrap-up is marked with `budgetWrapup: true` metadata.

A tool the model requests that is not in `config.tools` is refused: once per run with a tool-result message the model can recover from, otherwise the run fails with `tool '<name>' is not configured for this agent`.

### Failure-streak hints

`runtime/failure_guard.rs` watches single-call tool rounds. When the exact same call returns the same error, the same result, or the same sequence repeats three times, a hint is appended to the next system prompt telling the model to change approach or use the result. State lives only inside one invocation.

### Parallel tool execution

Tool calls from one model response run together with `join_all`. Each receives a clone of `AgentState`, the user `Message` and its `ToolCall`. Results are appended to the conversation in the order the model requested them.

### Step persistence

With a `DatabaseAdapter`, each tool call is written as a `Step` in two phases: `Pending` before execution, then `Done` or `Failed`. The idempotency key is a UUIDv5 over the agent id, the run id, the user message id, the room, the round, the call position and the call payload. If the input carries a `retryKey` / `retry_key` / `idempotencyKey` / `idempotency_key` in its metadata, the key uses that instead of the run id, so a re-run under a new host run finds the earlier steps and **reuses completed tool results** (`recovered: true` on `tool:after`). Persistence errors are non-fatal: they become `agent:message` events and the run continues.

## Stop and Steering

`RunControl { cancel: CancelSignal, steering: SteeringInbox }` is shared with the host by cloning.

- **Stop.** The runtime checks the signal before each model call, while streaming (dropping the request), and before each tool batch. Tools already running finish; every requested call that never ran gets the result `Cancelled before running (stopped by owner)`. Streamed text so far stays as an assistant message marked `stopped`. An owner stop returns `TaskResult::error("stopped")` and leaves the agent `Idle`. A helper deadline or daemon shutdown (`CancelCause::HelperDeadline`, `DaemonShutdown`) ends the run as failed with its own error text. The first cause wins.
- **Steering.** `SteeringInbox::push(content)` queues an owner message for the next model call; the runtime records it as a user message with `steer: true` and emits `RunFrame::Steered`. After `close()`, `push` gives the content back so the host can queue a new run instead.

## Live Frames

`RunObserver::on_frame` receives non-recorded `RunFrame`s: `StepStarted`, `TextDelta`, `StepUsage`, `ModelServed` (a fallback model answered), `StepFinished`, `ToolStarted`, `ToolFinished` and `Steered`. They never enter the stored event log. The daemon turns them into the SSE stream described in [Runs and Sessions](/hosts/rust-daemon/runs/). The observer runs inline and must not block.

Message metadata the runtime sets (constants in `runtime/observer.rs` and `control.rs`): `runId`, `stepId`, `revised`, `incomplete`, `stopped`, `steer`, `toolStatus`, `toolDurationMs`, plus `toolCalls` on assistant messages that requested tools.

## Concurrent Rooms

`run_snapshot`, `run_base`, `run_delta_since`, `apply_run_delta`, `revert_run_delta` and `retain_messages` (in `runtime/run_delta.rs`) let a host run several rooms of one agent at once on isolated copies, then merge exactly what each run added back into the canonical record, or undo it.

## State Transitions

| Method | Status change | Events |
|--------|---------------|--------|
| `mark_running()` | to `Running` | `agent:started`, `task:started` |
| completion | to `Completed` | `agent:completed`, `task:completed` |
| `mark_failed(...)` | to `Failed` | `agent:failed`, `task:failed` |
| `mark_cancelled(...)` for an owner stop | to `Idle` | `task:failed` |
| `stop()` | to `Terminated` | `agent:terminated` |

## Snapshots

```rust
pub struct AgentRuntimeSnapshot {
    pub state: AgentState,
    pub message_count: usize,
    pub messages: Vec<Message>,
    pub event_count: usize,        // all events ever recorded
    pub events: Vec<EngineEvent>,  // newest MAX_RETAINED_EVENTS (500)
    pub last_task: Option<TaskResult<Content>>,
    pub step_count: u64,
}
```

`AgentRuntime::snapshot()` captures it and `from_snapshot(snapshot, adapter)` rebuilds a runtime. The daemon stores snapshots in its control-plane store and, on restart, marks work that was running as interrupted rather than resuming it.

## Return Value

```rust
pub struct TaskResult<T> {
    pub status: TaskStatus,     // Success | Error
    pub data: Option<T>,
    pub error: Option<String>,
    pub duration_ms: u64,
}
```

`duration_ms` is measured from the start of the run and includes model calls, tools, providers and evaluators.
