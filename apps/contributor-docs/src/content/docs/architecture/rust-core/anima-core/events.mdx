The event system in `anima-core` is deliberately small: an enum of event types, a struct that carries them and one callback on `AgentRuntime`. There is no bus, queue or pub/sub inside the crate; the host decides transport. Live run progress uses a second, separate mechanism, [`RunFrame`](#run-frames).

## EventType

File: `packages/core-rust/crates/anima-core/src/events.rs`. `as_str()` gives the wire name.

| Variant | Wire name | Emitted by `AgentRuntime` |
|---------|-----------|---------------------------|
| `AgentSpawned` | `agent:spawned` | `init()` (not `new()`); data is the agent name |
| `AgentStarted` | `agent:started` | run begins |
| `AgentCompleted` | `agent:completed` | run succeeds; data is the reply text |
| `AgentFailed` | `agent:failed` | run fails; data is the error |
| `AgentTerminated` | `agent:terminated` | `stop()` |
| `AgentMessage` | `agent:message` | any message is recorded, and persistence-failure and tool-reuse notes |
| `TaskStarted` | `task:started` | run begins |
| `TaskCompleted` | `task:completed` | run succeeds |
| `TaskFailed` | `task:failed` | run fails, or an owner stop (agent returns to `Idle`) |
| `ToolBefore` | `tool:before` | before each tool call |
| `ToolAfter` | `tool:after` | after each tool call |
| `AgentTokens` | `agent:tokens` | after model calls and tool rounds; running totals |
| `SwarmCreated`, `SwarmCompleted`, `SwarmStopped` | `swarm:created`, `swarm:completed`, `swarm:stopped` | **Defined only.** Nothing in the workspace emits them; the daemon publishes its own swarm event names (see [HTTP API](/hosts/rust-daemon/api/)). |

## EngineEvent

```rust
pub struct EngineEvent {
    pub id: UuidString,           // "event-N"
    pub event_type: EventType,
    pub agent_id: Option<String>,
    pub timestamp_ms: u64,
    pub data: DataValue,
}
```

`DataValue` is a JSON-like enum (`Null`, `Bool`, `Number(f64)`, `String`, `Array`, `Object`) so events carry structured payloads without exposing `serde_json`.

Payloads:

| Event | `data` |
|-------|--------|
| `tool:before` | object: `name`, `args`, `status: "running"`, `durationMs: 0` |
| `tool:after` | object: `name`, `status`, `durationMs`, `recovered`, `result` |
| `agent:tokens` | object: `promptTokens`, `completionTokens`, `totalTokens` (cumulative for the runtime) |

## Typical Sequence

```
init()                         agent:spawned
run(...)                       agent:started, task:started, agent:message (user)
  per tool round               tool:before (each), tool:after (each), agent:message (tool results), agent:tokens
  final answer                 agent:message (assistant), agent:completed, task:completed, agent:tokens
```

Failure ends the sequence with `agent:failed` and `task:failed`. An owner stop emits `task:failed` with data `stopped` and leaves the status `Idle`. When a tool result is reused from persistence, an `agent:message` note precedes `tool:after`, which reports `recovered: true`.

## Retention

Every event is kept in the runtime and trimmed to the newest `MAX_RETAINED_EVENTS` (500; trimming runs in batches, so the in-memory list can briefly hold up to 64 more). `snapshot().event_count` is the running total, which can exceed `events.len()`. `events()` returns the retained slice.

## Listening

```rust
runtime.set_event_listener(Arc::new(move |event: EngineEvent| {
    let _ = tx.send(event);   // keep it fast: channel send, not I/O
}));
```

The listener runs **synchronously** inside event recording. Keep it to a channel send.

## Run Frames

`RunObserver::on_frame(RunFrame)` carries what the event log deliberately does not: streamed text and tool progress. Frames are never stored.

| Frame | Meaning |
|-------|---------|
| `StepStarted { step_id }` | A model call starts (`<runId>:<n>`, from `run_step_id`) |
| `TextDelta { step_id, text }` | Text the model streamed |
| `StepUsage { step_id, usage }` | Provider-reported usage |
| `ModelServed { step_id, provider, model, reason }` | A fallback model answered instead of the primary |
| `StepFinished { step_id, message_id }` | The call ended; the message it recorded, if any |
| `ToolStarted { step_id, tool_call }` | A tool starts (or is recovered from persistence) |
| `ToolFinished { step_id, tool_call_id, name, status, duration_ms, result, recovered }` | A tool finished |
| `Steered { message_id, text, content }` | A steered owner message joined the conversation |

The daemon maps these to its SSE events (`step.delta`, `tool.started`, `tool.finished`, `run.steered`, `model.fallback`, ...). See [Runs and Sessions](/hosts/rust-daemon/runs/).

## Host Pattern

The daemon uses `set_event_listener` only for **swarm** agents (`hosts/rust-daemon/src/state/swarm_runtime.rs`). Their `task:started`, `task:completed`, `task:failed`, `tool:before`, `tool:after`, `agent:tokens` and `agent:terminated` events are republished, with camelCase JSON payloads (`eventId`, `timestampMs`, `agentId`, `agentName`, ...), on the swarm SSE stream. Chat runs do not use the listener: the live agent stream (`GET /api/agents/{agent_id}/events`) is built from run frames and ledger changes. For those agents the in-runtime event log is mainly for snapshots and debugging.
